# Postman Collection Generator

Generates a production-ready Postman collection (v2.1 format) for non-regression API testing,
tailored for IBM integration stacks (APIC, ACE, MQ) at TCS Group / BCI Insurance.

This prompt is designed to work with user input that may include:
- OpenAPI / Swagger YAML or JSON
- Kibana traces / logs with request and response examples
- ACE services / applications
- ACE libraries / shared libraries
- ACE policy projects / policies / overrides
- payload samples
- implementation source files

The primary required output is the Postman collection JSON file.

Environment files are optional and should be generated only when they are useful or clearly needed.

Do not generate shell scripts, Jenkins files, CI/CD artefacts, or command-line helper files.

---

Run in **non-interactive batch mode** by default.

This means:
- Do **not** ask follow-up questions
- Do **not** ask for confirmation

If something is incomplete or ambiguous:
- continue with best-effort generation

Run these steps in order internally.

Internally summarise what is already known from the scope:
- API name
- direction
- catalogue(s)
- consumers
- likely auth model
- likely base URL variable

Do not output this summary unless it is helpful in file descriptions.

### Step 2 — OpenAPI/Swagger spec (mandatory evidence source)

Use the YAML or JSON spec as the primary contract when available.

Parse and determine:
- endpoint count
- groups/tags
- methods
- path parameters
- query parameters
- request schemas
- response schemas
- examples
- security model hints
- versioning/path structure

If the spec is missing but traces and ACE source are provided, continue best-effort and mention the limitation only if necessary.

### Step 3 — Kibana traces (strongly recommended)

Use Kibana traces when present.

They improve output dramatically by providing:
- real request payloads
- real response payloads
- actual APIC path shapes
- real status codes
- real headers
- correlation and language behavior
- scenario variants
- trace-proven examples for assertions

If traces are absent, fall back to schema-derived examples and ACE-derived logic.

### Step 4 — ACE/repository code (recommended and highly important)

If the user provides ACE services, ACE applications, ACE libraries, shared libraries, policy projects,
policy files, mappings, ESQL, JavaCompute, `.msgflow`, or related artefacts, you must analyze them deeply
to improve the Postman collection.

This is not optional enrichment when ACE source is present. It is a major evidence source.

The APIC API calls ACE services. ACE often contains:
- custom business validations
- conditional mandatory fields
- data enrichment
- provider routing logic
- request mapping
- response mapping
- error construction
- state checks
- defaulting logic
- policy-driven behavior

Therefore, the generated Postman requests must not only fit the OpenAPI schema.
They should also be adjusted, where possible, to pass or intentionally trigger ACE-side business validation.

### Step 5 — Scope and consumer confirmation (internal only)

If scope metadata was resolved in Step 0, treat it as default input:
- consumers
- catalogue
- base URL
- internal vs external auth model
- APIC path prefix when inferable

Do not ask the user to confirm.

Use the **Prerequisite & Data Dependency Chain** section below when needed.

# Generation Rules

Use this section immediately before generating JSON output. Do not ignore it.

---

## 1. Collection metadata

- `info.name`: `<API Name> - Non-Regression Tests`
- `info.schema`: `https://schema.getpostman.com/json/collection/v2.1.0/collection.json`
- Add a top-level `description` summarising the API and migration context
- If useful, mention that the collection was derived from:
  - OpenAPI / Swagger
  - Kibana traces
  - ACE implementation logic

---

## 2. Variables — never hardcode credentials or URLs

| Variable | Description |
|---|---|
| `{{url-apic}}` | Internal APIC (intranet) |
| `{{url-apic-external}}` | External APIC (internet) |
| `{{url-apic-tcs}}` | TCS new APIC stack |
| `{{url-apic-partner}}` | Partner gateway |
| `{{url-apic-public}}` | Public-facing gateway |
| `{{url-ace}}` | ACE direct — reference only, never use in requests |
| `{{url-oauth2-access-token}}` | Azure AD token endpoint |
| `{{client_id-x-{consumer}}}` | IBM Client ID per consumer |
| `{{client_secret-x-{consumer}}}` | IBM Client Secret per consumer |
| `{{bearerToken}}` | OAuth2 token (set by setup/auth flow if needed) |

Credentials always use Vault references where environment files are generated:
- `{{vault:client_id-q-{consumer}}}`
- `{{vault:client_secret-q-{consumer}}}`

Never hardcode:
- credentials
- secrets
- production hostnames as request targets
- internal backend URLs as collection targets

---

## 3. Folder structure

Group requests by **consumer** when consumer-specific auth or behavior matters.

If consumer grouping is not materially useful, group by functional domain/tag while keeping the collection easy to scan.

Example:
```text
Collection: insurance-claims-api-claims
└── 📁 TCS.CH Batch
    ├── OK - Post Insurance Claim
    ├── KO - Post Insurance Claim
    └── OK - Get Claim
```

If prerequisites exist:
```text
Collection: insurance-claims-api-claims
├── 📋 _README
├── 🔧 _SETUP
├── 📁 Claims
└── 🧹 _TEARDOWN
```

For internal + external split: generate **two separate collection files** only when justified.
- Internal: `<domain>-api-<resource>.postman_collection.json`
- External: `<domain>-api-<resource>-internet.postman_collection.json`

---

## 4. Request naming

- Happy path: `OK - <Description>`
- Error case: `KO - <Description>`
- Setup: `[SETUP] <Action>`
- Teardown: `[TEARDOWN] <Action>`

Use business-meaningful names.

Good:
- `OK - Create claim with valid active policy`
- `KO - Reject request when personalReference is missing`

Avoid vague names:
- `POST claim`
- `GET endpoint`

---

## 5. URL path structure

Use APIC base variables only.

General structure:
`{{url-apic}}/<domain>/<version>/<resource-path>`

Example:
`{{url-apic}}/insurance-claims/v2/claims/claim`

Domain segment derived from:
1. actual runtime path in traces
2. `x-ibm-name` or equivalent metadata in YAML
3. API name
4. conservative inference

Never target internal ACE listener URLs unless explicitly asked for ACE-direct testing, which is not the default.

---

## 6. Authentication

### Internal / intranet
Use IBM Client ID / Secret headers.

```json
"header": [
  { "key": "X-IBM-Client-Id", "value": "{{client_id-x-{consumer}}}", "type": "text" },
  { "key": "X-IBM-Client-Secret", "value": "{{client_secret-x-{consumer}}}", "type": "text" }
]
```

No `auth` block unless the API clearly requires one in addition.

### External / internet
Use OAuth2 client credentials + `x-tcs-client-id`.

```json
"auth": {
  "type": "oauth2",
  "oauth2": [
    { "key": "scope", "value": "{{client_id-x-{consumer}}}/.default", "type": "string" },
    { "key": "clientSecret", "value": "{{client_secret-x-{consumer}}}", "type": "string" },
    { "key": "clientId", "value": "{{client_id-x-{consumer}}}", "type": "string" },
    { "key": "accessTokenUrl", "value": "{{url-oauth2-access-token}}", "type": "string" },
    { "key": "grant_type", "value": "client_credentials", "type": "string" },
    { "key": "addTokenTo", "value": "header", "type": "string" },
    { "key": "client_authentication", "value": "body", "type": "string" }
  ]
},
"header": [
  { "key": "x-tcs-client-id", "value": "{{client_id-x-{consumer}}}", "type": "text" }
]
```

Note: external uses `x-tcs-client-id` (lowercase), **not** `X-IBM-Client-Id`.

Always include when relevant:
- `Accept`
- `Content-Type`
- `X-Correlation-Id: {{$guid}}`
- `Accept-Language`

## 7. ACE-aware generation rules

This is an additive rule set and must be applied whenever ACE artefacts are provided.

Do not rely on OpenAPI alone when ACE source is present.

You must understand ACE components deeply enough to improve the correctness of the generated tests.

### ACE expertise expected

You are expected to analyze and understand:
- ACE 12 applications
- libraries
- shared libraries
- policy projects
- policies and overrides
- message flows
- subflows
- generated flows
- REST descriptors
- node wiring
- node terminals
- node properties
- node behavior
- ESQL
- JavaCompute
- mapping nodes
- message domains
- HTTP/REST integrations
- error handling
- monitoring events
- Environment / LocalEnvironment usage

### What to extract from ACE

Look for:
- entry points and operations
- route-to-label patterns
- branching logic
- node sequence and terminal routing
- ESQL `IF`, `CASE`, `COALESCE`, null checks, blank checks, existence checks
- required object and field checks
- conditional mandatory fields
- cross-field dependency rules
- enum-like accepted values
- formatting rules
- default values
- field derivations
- value translations
- mapping logic
- Environment / LocalEnvironment population and usage
- policy-driven endpoint or behavior selection
- outbound provider request mapping
- inbound provider response mapping
- error message construction
- business error code construction
- success response construction
- retry/propagate/batch coordination when visible
- common/reusable subflow logic
- shared-library dependencies

### How ACE findings must influence the collection

Use ACE findings to:
- choose realistic valid values for OK tests
- construct precise invalid values for KO tests
- infer hidden mandatory fields not visible in OpenAPI
- infer conditional rules not visible in schema
- detect business validations that reject schema-valid payloads
- infer field combinations that must appear together
- infer state prerequisites
- infer business error structures when visible
- improve response assertions when mapping logic is visible
- align request examples to what ACE actually expects after APIC mediation

### Important limitations

- Do not invent validations not visible or reasonably inferable
- If logic is referenced through shared libraries but not visible, treat it as inferred only
- Do not claim exact business error codes unless visible in source or traces
- Do not dump ACE source into the output
- Do not document ACE internals unless needed to improve the collection

### APIC-first rule

Even when ACE reveals internal details, the generated requests must validate the APIC-exposed API behavior.
ACE is supporting evidence, not the target endpoint.

## 8. Test scripts

Add test scripts to every request.

### Baseline status/time checks

Use the most specific expected status code possible.

For OK requests:
- assert the exact success code when known
- otherwise use a narrow allowed set only if justified

For KO requests:
- assert the exact error code when known
- otherwise use the most likely stable code from source/traces

Example success:
```javascript
pm.test("Status code is expected", function () {
    pm.expect(pm.response.code).to.eql(201);
});
pm.test("Response time is acceptable", function () {
    pm.expect(pm.response.responseTime).to.be.below(5000);
});
```

Example flexible success when justified:
```javascript
pm.test("Status code is expected", function () {
    pm.expect(pm.response.code).to.be.oneOf([200, 201, 202]);
});
```

### Schema validation

Add when response schema is known:
```javascript
const schema = { /* inline JSON Schema */ };
pm.test("Response matches schema", function () {
    pm.expect(tv4.validate(pm.response.json(), schema)).to.be.true;
});
```

### Trace-based assertions

Add when Kibana trace provides expected values:
```javascript
pm.test("Response contains expected fields", function () {
    const j = pm.response.json();
    pm.expect(j).to.have.property("orderId");
    pm.expect(j.status).to.eql("CONFIRMED");
});
```

### Migration non-regression assertions

Add when backward compatibility matters:
```javascript
pm.test("Response structure is backwards compatible", function () {
    const j = pm.response.json();
    ["field1", "field2", "field3"].forEach(f => pm.expect(j).to.have.property(f));
});
```

### KO assertions

If error structures are visible from traces or ACE:
- assert status code
- assert error code/message fields when stable
- do not over-assert unstable free-text messages

Example:
```javascript
pm.test("Status code is expected", function () {
    pm.expect(pm.response.code).to.eql(400);
});
pm.test("Error response contains code", function () {
    const j = pm.response.json();
    pm.expect(j).to.have.property("code");
});
```

## 9. Kibana trace handling

- Use request body values verbatim when suitable and safe as examples
- Use response body to generate field-level assertions
- Infer headers from trace where relevant
- Multiple traces for the same endpoint → create multiple request variants when they are meaningfully different
- Production hostname from trace → never hardcode, always replace with the correct base URL variable
- Preserve path and query structure from traces when likely canonical
- Prefer actual traced status codes over generic assumptions when consistent

If a trace clearly reflects APIC-transformed or ACE-transformed payloads, favor that runtime shape for assertions.

---

## 10. APIC gateway — hard constraint

**ALL requests MUST target the APIC URL. Never call internal ACE URLs directly.**

APIC enforces security policies, rate limiting, and may apply transformations on top of ACE.
A test bypassing APIC does not validate what consumers actually experience.

---

## 11. ACE flow inputs

Use ACE artefacts only to inform test content:
- field names, mandatory/optional logic, and data types
- business validation understanding
- transformation logic
- error code and fault-message understanding where visible
- prerequisite state inference
- response mapping understanding
- async acknowledgment behavior

MQ internal calls are invisible to Postman.
Test only the synchronous HTTP response unless a visible status/polling API exists.

---

## 12. MQ-backed / async APIs

- Call the APIC HTTP endpoint normally
- Assert `202 Accepted` when appropriate
- Assert any correlation/tracking ID if present
- Add description: "This request triggers an async MQ process. Verify functional completion separately."
- If a polling/status endpoint exists, add it as a follow-up request

Do not fabricate completion checks when the system does not expose them.

---

# IDIT Domain Reference

IDIT is the **Sapiens IDIT** Policy and Claims Administration System used by TCS.
It is being migrated from an on-premises version to a SaaS version, with a major version upgrade.
The migration involves rebuilding integrations via IBM APIC/ACE/MQ.

This reference captures the key domain entities, their relationships, the main APIs exposed or consumed
by IDIT, and the prerequisite data dependencies relevant for non-regression testing.

---

## System context

IDIT sits at the center of an integration ecosystem that includes:
- Salesforce
- SAP
- SIX
- La Poste / BVR
- ECM
- KOFAX
- ASSYS / ALIS
- DPM
- Azure Active Directory
- BI
- IPS V1/V2, Travel Safety, Protect-ID
- eCommerce / e-care
- Various Sales GUIs

---

## Core domain entities and their relationships

### Contact (Client)
- A **Contact** is a person or legal entity
- Contacts are typically mastered in Salesforce and synced to IDIT
- **A contact must exist before any policy, proposal, or claim can be created**

### Policy / Proposal
- A **Proposal** is a quote/basket not yet issued
- A **Policy** is an issued insurance contract
- A policy belongs to exactly one **Contact**
- A policy may have covers, beneficiaries, endorsements, and cancellation
- **A contact must exist before a policy can be created**

### Endorsement / Cancellation
- Both require an existing active policy
- Reasons are reference-data driven

### Claim / Loss Event
- A **Claim** requires an existing contact and active policy
- Claims may have external system references

### Invoice / Payment Slip
- Payment artifacts depend on policy issuance / invoice generation

### Basket / Cart (HUI)
- Used in eCommerce
- Validation may perform underwriting checks
- Policies are issued after validation

---

## Prerequisite dependency chains

### Chain 1: Contact only
```text
Contact exists in IDIT
└── Get Contact
└── Get Portfolio
└── Get Proposals List
```

### Chain 2: Contact + Policy
```text
Contact exists
└── Active Policy exists
    └── Get Policy
    └── Get Endorsement
    └── Get Payment Slip
    └── Get Portfolio
```

### Chain 3: Contact + Policy + Claim
```text
Contact exists
└── Active Policy exists
    └── Loss Event / Claim exists
        └── GET Loss Events/Claims
```

### Chain 4: Contact + Basket/Proposals
```text
Contact exists
└── Proposal(s) exist in basket
    └── Validate Cart
    └── Issue Policy List
    └── POST /online-payment
```

### Chain 5: Contact + Policy + Invoice
```text
Contact exists
└── Policy exists and invoice has been generated
    └── Get Invoice
    └── Get Payment Slip
    └── Incoming Payment
```

## Reference data (must be pre-configured in the system)

The following may need to exist before tests can run:
- products and product versions
- covers and cover types
- cancellation and endorsement reasons
- payment methods
- service provider types and territories
- entity types
- contact titles
- family relationship types
- contact sub-types
- sales channels / intermediaries
- GL mapping
- language

- ACE transformations may make runtime payloads differ from raw IDIT/provider schemas
- Some integrations are async via MQ
- Always send `X-Correlation-Id`

## The BCI Insurance entity chain

```text

       ↓  (contactId)

       ↓  (policyId / proposalId)

       ↓  (policy moves to ACTIVE status)

       ↓  (policyId, updated state)

       ↓  (claimId)
```

## Option A — Auto-setup (_SETUP folder)

Generate a `🔧 _SETUP` folder only when supported by the provided artefacts.

```text
Collection: insurance-claims-api-claims
├── 📋 _README
├── 🔧 _SETUP
│   ├── [SETUP] Create Contact          → extracts {{contactId}}
│   ├── [SETUP] Create Policy           → extracts {{policyId}}
│   └── [SETUP] Verify Policy is ACTIVE → sets {{setup_policy_ok}}
├── 📁 Claims
│   ├── OK - Post Claim
│   └── KO - Policy not ACTIVE
└── 🧹 _TEARDOWN (optional)
    └── [TEARDOWN] Cancel Policy
```

Setup request test script pattern:
```javascript
pm.test("Contact created", () => pm.response.to.have.status(201));
const contactId = pm.response.json().contactId;
pm.environment.set("contactId", contactId);
pm.environment.set("setup_contact_ok", true);
```

Downstream pre-request guard:
```javascript
if (!pm.environment.get("setup_contact_ok")) {
    throw new Error("❌ SETUP ABORTED: run [SETUP] Create Contact first.");
}
```

Use `{{mustProvide_policyId}}`, `{{mustProvide_contactId}}` when setup cannot be reliably generated.

```javascript
["mustProvide_contactId", "mustProvide_policyId"].forEach(v => {

        throw new Error(`❌ Missing: ${v}. Set it in your environment before running.`);
```

```text
## Before running

```
