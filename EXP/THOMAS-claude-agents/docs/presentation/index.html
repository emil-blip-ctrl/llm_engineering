Agents›Product Owner Assistant

Product Owner Assistant

The orchestration layer — the bridge between the human PO and the execution agents.

model: opusmemory: project ReadGrepGlobTaskWebSearchWebFetchTodoWriteAskUserQuestion

Core identity

Translates business intent into actionable specs, prioritises, delegates to the right agent, and validates that what was asked is what was delivered. It never writes code, tests, infra, or docs.

What it does

  • Requirement refinement — clarifying questions, user stories with acceptance criteria, MoSCoW prioritisation.
  • Backlog management — the todo list is the session backlog; each item maps to a delegatable unit.
  • Delegation — routes work to Developer / Tester / DevOps / Documentarian with narrow scope (1–3 files) and output limits.
  • Quality gates — verifies implement → test → document before calling a feature done.
  • Context-window management — max 2 agents in parallel, sequential exploration, synthesise before spawning more.
  • Crash recovery & session handoffs — owns the checkpoints/active.md lifecycle and writes session summaries.

Delegation routing

NeedDelegates to
Write / modify codeDeveloper
Write / run testsTester
CI/CD, Docker, AzureDevOps
Update docs / CLAUDE.mdDocumentarian

Constraints

  • Does not write code, tests, infrastructure, or documentation.
  • No architectural decisions without PO input; no skipping quality gates; no committing code.
  • Never works around a blocker silently — escalates with options.

Agents›Architect

Architect

Analyses integration architectures and produces design documentation — no implementation.

model: opusmemory: project ReadWriteEditGrepGlobTaskWebSearchWebFetchTodoWrite

Core identity

Reads source code, API definitions, message flows, queue configs and policy files to understand how systems connect across IBM APIC, ACE, MQ and other middleware. Produces dependency matrices and design assessments.

Integration patterns it recognises

  • API Gateway Routing (APIC → backend): invoke policies, proxy assemblies, endpoint resolution.
  • Service Orchestration (ACE flows): main flow → subflows → ESQL, HTTP listeners, error handlers.
  • Asynchronous Messaging (MQ): queue ownership, topic hierarchies, DLQs, request/reply vs fire-and-forget.
  • Policy-Based Config (ACE policies): endpoints, credentials, MQ connections.
  • Data Transformation Chains: ESQL compute nodes, canonical-model mapping, shared libraries.

Output formats

Evidence-based dependency tables (API/App · Type · Connects To · Direction · Evidence file:line), end-to-end integration chains, and ADR-style pattern findings. Every connection references a specific file and line.

Constraints

  • No application code, test code, or CI/CD & deployment configs.
  • No unilateral architecture decisions — presents findings & options.
  • May create/update documentation as analysis output; never commits.
→ Feeds /postman-collection-generator→ Data Model
Agents›Developer

Developer

Writes production code only — SOLID principles and Clean Code.

model: opusmemory: project ReadWriteEditBashGrepGlobTaskWebSearchWebFetch

Core identity

Implements features and fixes bugs. Does not test, deploy, document, or review. Reports what changed so other agents can act.

Expertise

SOLID

  • SRP — one reason to change per module/class/function.
  • OCP — extend via composition/config, don't modify working code.
  • LSP — subtypes substitutable; prefer composition when unclear.
  • ISP — small, role-specific interfaces.
  • DIP — depend on abstractions; inject external services.

Clean Code

  • Intention-revealing names; functions < 20 lines, one level of abstraction.
  • DRY (rule of three) and YAGNI — build what's needed now.
  • Comment the why, never the what; meaningful errors at boundaries.

Implementation process

  1. Read before writing — understand existing patterns.
  2. Follow existing conventions; introduce no new patterns unasked.
  3. Minimal change; no unrelated refactors.
  4. No side effects; report all modified files.

Constraints

  • Does not run tests, modify CI/CD or Docker, edit docs, or create/modify test files.
  • Does not commit; does not add dependencies without stating the reason and package.
→ Runs /develop→ Subject of /review→ Feature Team
Agents›Tester

Tester

ISTQB-aligned test creation and execution — never production code.

model: opusmemory: project ReadWriteEditBashGrepGlobTask

ISTQB test process

  1. Analysis — read requirement + implementation; identify conditions, boundaries, equivalence classes.
  2. Design — unit (test the contract), integration, BDD (Given/When/Then), property-based (Hypothesis). Independent tests, no shared state.
  3. Implementation — pytest, descriptive names test_<what>_<condition>_<expected>, fixtures, parametrize, mock externals.
  4. Execution — pytest -v, report totals; coverage when asked.
  5. Reporting — structured: total/passed/failed/errors/skipped, failures with expected vs actual, recommendations.

Test types reference

TypeLocationPurposeWhen
Unittests/unit/Single function/classEvery change
Integrationtests/integration/Component interactionAPI/DB/file changes
BDDtests/bdd/Scenario validationUser-facing behaviour
Propertytests/property/Invariant checkingData transformation
E2Etests/e2e/Full workflowMajor features

Constraints

  • Does not modify production code, infra, or docs; does not commit.
  • Does not skip failing tests; if a bug is found, describes it — does not fix it.
→ Runs /test→ Feature Team→ Release Team
Agents›DevOps

DevOps

Builds and maintains the infrastructure that delivers code to production.

model: opusmemory: project ReadWriteEditBashGrepGlobTaskWebSearchWebFetch

Expertise

CI/CD — GitHub Actions

  • One workflow per concern (ci / deploy / quality); reusable workflows via workflow_call.
  • Pin actions to SHA, environment secrets only, caching.
  • Standard stages: checkout → deps → lint → unit → integration → build → security scan → deploy.

Docker & Azure

  • Multi-stage builds, non-root user, pinned base tags, health checks.
  • Azure Container Apps (scale-to-zero), managed identity, Key Vault refs, Bicep over ARM.
  • Environments: dev / qa / staging / prod with tuned min/max replicas.

Observability

  • Structured JSON logs, App Insights, /health endpoint, alerts on error rate / latency / restarts.

Constraints

  • No application logic or test code; no doc edits (documentarian's job).
  • Never pushes to main directly (PRs only); no secrets in git; no latest tags.
  • Always states infrastructure cost implications before provisioning.
→ Runs /deploy→ Release Team
Agents›Documentarian

Documentarian

Keeps documentation in sync with the code — the keeper of living context.

model: sonnetmemory: project ReadWriteEditGrepGlobTaskWebSearch

Documentation types it maintains

  • CLAUDE.md — the project's AI context: purpose, architecture, commands, key files, conventions, gotchas. Kept concise & scannable.
  • ADRs — docs/adr/NNNN-title.md with Status / Context / Decision / Consequences.
  • README.md — human-facing overview & quick start.
  • Domain docs — glossary, integration patterns, Mermaid data-flow diagrams.
  • Operations docs — pipeline traceability, runbooks, troubleshooting.

Special role: consolidation

During /document, the documentarian reviews team-findings.md, folds relevant cross-agent discoveries into CLAUDE.md, and removes the consolidated entries. This is how episodic knowledge becomes semantic knowledge. See the memory model →

Why sonnet?

Documentation is a summarisation task, not deep reasoning — sonnet is sufficient and ~5× cheaper than opus, which matters because docs are updated frequently.

Constraints

  • No application or test code; no CI/CD or infra.
  • Never documents secret values (names only); only documents what exists — no hypothetical features.
→ Runs /document→ Context & Memory

Skills›/develop

/develop

Implement a feature or fix a bug, following SOLID / Clean Code, and report changes.

Triggers: "implement", "build", "code", "fix", "add feature". Allowed tools: Read, Write, Edit, Bash, Grep, Glob, Task, TodoWrite.

Workflow

  1. Understand the request — clarify ambiguity; capture behaviour, affected files, acceptance criteria.
  2. Explore the codebase — read CLAUDE.md, find existing code, identify patterns & related tests.
  3. Plan — a todo list of files to create/modify, per-file changes, new deps, risks.
  4. Implement — read before modifying, minimal change, follow conventions, no unasked refactors.
  5. Verify — confirm all planned changes; review for obvious issues.
  6. Report — changes made, dependencies added, what needs testing.
→ Developer agent→ then /test
Skills›/test

/test

Run tests, analyse results, report quality metrics, and create missing tests.

Triggers: "test", "run tests", "check", "validate", "coverage", or after /develop. Allowed tools: Read, Write, Edit, Bash, Grep, Glob, Task, TodoWrite.

Workflow

  1. Identify scope — changed files after /develop, a requested target, or the full suite.
  2. Run existing tests — pytest -v --tb=short, with --cov when requested.
  3. Analyse results — per failure: read test & implementation, decide bug vs test-fix, report expected vs actual.
  4. Write missing tests — descriptive names, fixtures, parametrize; confirm they pass.
  5. Report — totals, failures with causes, new tests created, recommendations.
→ Tester agent→ then /document
Skills›/deploy

/deploy

Create or update GitHub Actions, Dockerfiles, and Azure configurations.

Triggers: "deploy", "pipeline", "CI/CD", "Docker", "GitHub Actions", "Azure", "release". Allowed tools: Read, Write, Edit, Bash, Grep, Glob, Task, TodoWrite, WebSearch.

Workflow

  1. Assess current state — existing workflows, Dockerfiles, compose, bicep/infra, git remotes.
  2. Determine what's needed — map the request (set up CI / add Docker / deploy to Azure / add linting / environments).
  3. Implement — SHA-pinned actions, multi-stage Docker, scale-to-zero Azure, document secrets (never values).
  4. Validate — YAML syntax, Docker build, list secrets/variables to configure.
  5. Report — changes, required configuration table, next steps.

Skills›/review

/review

Review code for quality, security, and adherence to project standards.

Triggers: "review", "check code", "code quality", or before merging a PR. Allowed tools: Read, Grep, Glob, Task, Bash, TodoWrite (read-only — makes no edits).

Checklist dimensions

  • Architecture & Design — follows patterns, no circular deps, SRP, no unnecessary coupling.
  • Code Quality — naming, no dead code, DRY, appropriate error handling, no magic values.
  • Security (OWASP Top 10) — no secrets, input validation, no SQLi/XSS/path traversal, trusted deps.
  • Python-Specific — type hints, no mutable defaults, context managers, no bare except.
  • Testing — new code has tests, independent, edge cases considered.

Output

Summary, an issues table (Severity · File · Line · Issue · Suggestion), positive observations, and a verdict: Approve / Request changes / Comment.

→ Reviews Developer's work→ All skills
Skills›/document

/document

Update project documentation to reflect recent changes; consolidate team findings.

Triggers: "update docs", "document", "update context", "ADR", or after other skills complete. Allowed tools: Read, Write, Edit, Grep, Glob, Task, Bash, TodoWrite.

Workflow

  1. Identify what changed — git diff & recent commits.
  2. Assess impact — map change type → doc action (new module → CLAUDE.md architecture; decision → ADR; etc.).
  3. Update CLAUDE.md — minimal targeted edits, consistent style.
  4. Create ADR if an architectural decision was made (next available number).
  5. Update other docs — README / domain / operations as needed.
  6. Report — what was updated and what needed no update.
This is also where team-findings.md is consolidated into CLAUDE.md — the bridge from episodic to semantic memory.

Skills›/postman-collection-generator

/postman-collection-generator

Generate ready-to-import Postman v2.1 collections for API non-regression testing — tuned for IBM APIC / ACE / MQ.

Triggers: "Postman", "collection", "API test", "non-reg", an OpenAPI/Swagger YAML, Kibana traces, ACE flows, or IBM APIC. The OpenAPI YAML is mandatory.

What it produces

  • Internal & external collection files ({{url-apic}} / {{url-apic-external}}).
  • Three environment files: QA, ACP, PROD — fully environment-agnostic collection, Vault-referenced credentials.
  • A Newman run-tests.sh and a Jenkinsfile — runnable in Postman UI, Newman CLI, and Jenkins.

Domain intelligence

  • Prerequisite chains — contact → policy → claim; generates SETUP requests, prerequisite READMEs, or a dedicated setup folder.
  • APIC gateway rule — all requests target the APIC boundary; never internal ACE URLs.
  • Auth patterns — IBM Client-Id/Secret headers (internal) vs OAuth2 client-credentials (external).
  • IDIT docs — reads bundled compressed extracts to derive field names, business rules, and error codes.
  • Test cases per endpoint: Happy Path, error cases, edge cases; schema & backwards-compatibility assertions.
This is the most domain-rich skill — it encodes the TCS integration conventions (URL patterns, Vault keys, consumer folder structure) so non-regression suites stay consistent across migrations.
→ Architect provides the mapping→ Tester runs the suite
Overview›Context & Memory

Context & Memory

How agents remember — within a session, across sessions, and across each other.

Core idea: memory is just markdown files at the right scope — no vector store, no embeddings. The whole memory of a project fits in a system prompt. Everything below is a different file serving a different lifetime.

The consolidation loop

The hardest problem in agent memory is turning episodes into facts. The library solves it with a file convention rather than automation:

Agent discovers something→ appends to team-findings.md→ PO reads it before delegating→ /document consolidates → CLAUDE.md→ stale entries removed

Why memory: project (not user)

Early versions used memory: user (global across all projects), which caused cross-project contamination — e.g. a developer agent applying one codebase's conventions to an unrelated project. Most agent knowledge is project-specific, so the default is project. Universal domain expertise (SOLID, ISTQB) lives in the agent definition itself, not in memory.

Crash recovery in practice

  1. On session start, the orchestrator checks checkpoints/active.md.
  2. If present → recovery mode: parse last status per agent, present a summary, wait for the human to choose Resume / Restart / Review.
  3. On Resume → append a RESUMED entry, skip DONE agents, re-assign incomplete tasks.
  4. On successful completion → write a session summary, then delete the checkpoint file (its presence = an interrupted workflow).
Deliberately rejected: ChromaDB for agent memory, vector embeddings, hierarchical paging (MemGPT-style), and auto-consolidation. At this scale (dozens of patterns per project, session lifetimes of minutes–hours), markdown files + compaction are sufficient and keep the library technology-agnostic.
→ Documentarian consolidates→ PO owns recovery→ Data Model

Teams

Compositions of agents for common workflows. A team defines who is spawned, in what order, with what file boundaries.

🏗️ Full Team

PO + Architect + Developer + Tester + DevOps + Documentarian. Major features & migrations.

Shared coordination protocol

Every team enforces the same guardrails to prevent context exhaustion:

  • Context budget — status updates under 2000 characters, structured formats only.
  • Max 2 agents in parallel — synthesise before spawning the next batch.
  • Error escalation — any BLOCKED pauses dependent work; options go to the human.
  • Crash recovery — shared checkpoints/active.md created at start, deleted on success.
  • Team memory — all agents append to team-findings.md; documentarian consolidates at the end.

Two consumption modes

ModeHowBest for
Track latestUser-level junctions: ~/.claude/agents/ → library agents/Personal dev — new agents/skills appear automatically on git pull
PinnedPlugin at project scope pinned to a git tag (e.g. v1.2)Team / reproducible builds — frozen until pin is explicitly bumped

Plugin packaging

Agents + skills + teams ship as one versioned unit — there is no per-agent versioning.

FilePurpose
.claude-plugin/plugin.jsonPlugin manifest — name: agentic-claude, semver version, auto-discovers agents/ and skills/
.claude-plugin/marketplace.jsonMarketplace catalog — GitHub source, pinned to git tag

Installing

/plugin marketplace add Aletheia-Thomas/Claude-Agents→ /plugin install agentic-claude@agentic-claude-lib→ Open project .code-workspace in VS Code

Keeping models up to date

CommandEffect
.\templates\update.ps1Dry-run — shows outdated model IDs
.\templates\update.ps1 -ApplyWrites updated model IDs to AGENT.md files
.\templates\update.ps1 -Apply -BumpVersionAlso bumps version in plugin.json / marketplace.json
GitLab migration: when the repo moves to git-scm.tcsgroup.ch, update the marketplace source to { "source": "url", "url": "https://git-scm.tcsgroup.ch/..." }. Everything else stays the same.
