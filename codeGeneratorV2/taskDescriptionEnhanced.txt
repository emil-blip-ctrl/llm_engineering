# Description

**As** tcs.ch, **I want** to create a Roadside Assistance (RSA) claim through the `insurance-claims` API, including the vehicle, the driver and the declared amount, **so that** the claim is created in IDIT through the new manageClaims endpoint, while Personal Assistance (PA) claims keep using loss-event unchanged.

## Context

- **RSA** claims from tcs.ch must be sent to `POST /api/v2/loss-event/manage-claims`.
- **PA** claims from tcs.ch keep using `loss-event`, unchanged.
- A claim is RSA when it carries a vehicle, PA otherwise. Product 103 can be either.
- MOEx chooses the route through configuration. The consumer sees no difference: same endpoint, same contract, same responses.
- Go-live: November 2026.

The yaml differs on these points (payload validation disabled since 2.0.4). **Do not change the existing ACE parsing.**

### Business rules

| # | Rule | Hosted in |
|---|---|---|
| B1 | A claim is **RSA when it carries a vehicle, PA otherwise**, for every product (103 can be either). The consumer flags it with `attributes[type=claim-use-case].value-code = RSA`. Missing or `PA` means PA. Any other value is rejected. | ACE — validation |
| B2 | An RSA claim carries exactly one vehicle (`damaged-objects-details.vehicle[]`, one item). | ACE — validation |

## 2. Conventions and global constraints

### Path notation

- Input and output paths use JSON dot notation.
- `[0]` means the first array item.
- `[]` means an array of items.
- `claim-contacts[role=driver]` selects the contact whose role is `driver`.
- `attributes[type=X].value-code` selects the `value-code` of the attribute whose type is `X`.
- `—` in the input column means there is no BOM input field: the value is generated or injected.
- All target paths below are fully expanded, including targets abbreviated with `…` in the workbook.

### IDIT requirements

| Code | Meaning |
|---|---|
| M | Mandatory on the manageClaims side |
| C | Conditional on the manageClaims side |
| O | Optional on the manageClaims side |

`VO` is retained as the workbook's type label. The target path identifies the corresponding `extCode` field.

### Translation constraints

1. A **constant** is injected by MOEx and must never be read from the BOM.
2. Any BOM data not listed in the translation rules is **not transmitted**.
3. Input paths reflect the payload format actually sent by tcs.ch today:
   - `claimed-damages` is an array.
   - `reimbursement` is an array.
   - The cause-of-loss field is `primary-cause-of-loss-extcode`, with lowercase `c`.
   - Attributes may contain only `type` and `value-code`.
4. The YAML differs from the actual input format on these points. Payload validation has been disabled since 2.0.4. **Do not “correct” the existing ACE reading to match the YAML.**
5. The PA `loss-event` route retains its legacy translator unchanged, including its own values such as `polHold`, `1`, and `INTERFACE`. **Never mix the RSA and legacy translation tables.**
6. Preserve the spelling and capitalization of field names, codes, and string identifiers, including leading zeros in examples.
