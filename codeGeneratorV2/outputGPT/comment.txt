Implemented the phase-1 routing rules in the facade with ordered first-match behavior and environment-driven activation flags.

Changed:
- Added new shared compute module:
  - `common/prepareNoContentResponse_Compute.esql`
  - Prepares an empty HTTP response with status `204`.
- Updated routing/filter ESQL:
  - `create_case_IsAssys_Filter.esql`
  - `createUpdate_service_IsAssys_Filter.esql`
  - `update_case_IsAssys_Filter.esql`
  - `MessageFilter_FilterFSMMessage.esql`
- Updated subflows to support “exit process / log error and exit process” without invoking a backend:
  - `create_case.subflow`
  - `create_service.subflow`
  - `update_service.subflow`
  - `update_case.subflow`
- Updated policy project to add and populate `assys-activated` and to align `sfcas-activated` values:
  - `SfcasCredentialsPolicy.policyxml`
  - `properties/DEV.properties`
  - `properties/QA.properties`
  - `properties/ACP.properties`
  - `properties/PRD.properties`

Behavior implemented:
- Rule order is evaluated with `IF / ELSEIF` so processing stops at the first true rule.
- All string comparisons are case-insensitive via `UPPER(TRIM(...))`.
- Routing decisions are logged into `Environment.Variables.TCSLog.context`:
  - routing-endpoint
  - routing-rule
  - routing-action
  - routing-detail
  - routing-target
  - routing-case-id / routing-consumer-* where relevant
- Post Case supports:
  - policy-based Assys/SFCAS redirection
  - SPARX exit
  - ContextList rules for DIRCALL / RSATCS, DIRCALL / RSAB2B, ONLINEASSY, B2B consumer list, MLOG
  - default Assys
- Put Case / Post Service / Put Service supports:
  - policy-based Assys/SFCAS redirection
  - SPARX + 9-digit case-id exit
  - DRAPP + 9-digit case-id logged error exit
  - 9-digit case-id => Assys
  - non-9-digit case-id => SFCAS
  - default Assys

Assumptions / limitations:
- I assumed the DRAPP rule row in the story contains a typo and should use `DRAPP` instead of `SPARX`. I implemented `DRAPP`.
- “exit process” and “log an error and exit process” were ambiguous from an HTTP contract perspective. I implemented both as an immediate `204 No Content` response and, for the DRAPP case, logged it with `severity = ERROR` in the monitoring context.
- For Post Case, I preserved the existing FSM-specific Assys path selection by keeping `MessageFilter_FilterFSMMessage`; I only made it robust for both `$.case.ContextList[]` and the older `$.ContextList[]` shape.
- I did not change the generated REST msgflow or OpenAPI descriptor because the operation structure remains unchanged.
