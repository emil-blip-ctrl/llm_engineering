# US NIPO\-9498 Sansys \- Routing \- Invoice Ingestion to Financial Document V2

**Ticket:** [NIPO-9498](https://tcsgroup.atlassian.net/browse/NIPO-9498) · **Owner:** Integration engineer · **Status:** design complete — ready for build

**Design references:** [ADR-0001](https://tcsgroup.atlassian.net/wiki/spaces/CS/pages/2265776280) (tenancy vs functional layer), [ADR-0009](https://tcsgroup.atlassian.net/wiki/spaces/CS/pages/2266333273) (company-neutral process\_control)

**Scope:** only the routing policy-property tuple in `finance-accounting-integration-invoices-policy-project`. The `process_control` value is emitted by [NIPO-9422](https://tcsgroup.atlassian.net/wiki/spaces/ARCHI/pages/2232615118/US+NIPO-9422+Sansys+-+File+to+Invoice+Ingestion); SAP dispatch is [SAPS-2744](https://tcsgroup.atlassian.net/wiki/spaces/ARCHI/pages/2265776241/US+SAPS-2744+AIF+producer_app+carriage); `producer_app` stamping is [NIPO-9499](https://tcsgroup.atlassian.net/wiki/spaces/ARCHI/pages/2233008237/US+NIPO-9499+Sansys+-+Financial+Document+V2+to+S_FIN_DOC).

## Why

The ACE routing layer resolves every outbound target by looking up policy properties named `{sender_id}_{process_control}_{attr}` — a data-driven lookup, not a code branch. There are two parallel routing apps sharing the same policy project: v1 (`finance-accounting-integration-invoices`, kebab-case, today's Attrib path) and v2 (`finance-accounting-integration-invoices-v2`, camelCase). Sansys's EOM v2 mapper output only resolves cleanly through **v2**, so this story adds one new property tuple for Sansys traffic — no code change to any shared app.

Key mechanics (identical in both apps):

- `sender_id` = the inbound `X-Origin-Caller-Code` header — the **caller** of the ACE entry point, not the source app. VTOM drives the Sansys trigger, so the caller is `VTOM` (same as the live Attrib rows).
- Routing key = `lower(sender_id || '_' || process_control || '_' || attr)`, with 5 attributes per tuple: `_target`, `_application`, `_endpoint`, `_timeout`, `_call`.
- Naming trap: `_endpoint` is a **host** alias and `_application` is a **path** alias — the reverse of what the names suggest.

## What

- One new policy-property tuple `vtom_ambulance_transport_billing_{target,application,endpoint,timeout,call}` — **one tuple for all 6 companies** (`process_control` is company-neutral; per-company visibility lives in the AIF hierarchy, not in routing).
- No `SANSYS.policyxml` — the caller stays `VTOM`, whose (empty, mandatory) policy file already exists.
- Attrib's 3 existing tuples untouched.

**Definition of done:** the `common.policyxml` diff shows exactly 5 new properties and no other row touched; a test call with `X-Origin-Caller-Code: VTOM` and `process_control = AMBULANCE_TRANSPORT_BILLING` resolves to the v2 technical app without a `422`.
