Summary

This issue involves developing a new API, services-api-sfcas-cases-assessment, that will serve SFCAS as the consumer. The API will include two endpoints for handling waiting time and quoting services.

Context

This API enables CAS (SFCAS) to query FSM for waiting time estimates and tariff zone information
for assistance cases. It acts as a consumer-facing facade over the existing provided API
external-api-fsm-assistance-cases, translating between the SFCAS Salesforce data model and
the internal Assistance Business Object Model (BOM).

The implementation depends on:

A new ACE integration application services-integration-assistance-cases-sfcas-assessment (CMDB: CMP35366)

An update of the ACE shared library services-integration-shlib-transform-sfsc-bom for SFCAS↔BOM translation (NIPO-8456, NIPO-8457)

The existing shared library common-integration-shlib-datavalue-transcoding

The SFCAS Salesforce data model is not yet defined. Until it is, no payload validation can be performed and any valid JSON object is accepted.



Developer Tasks:

Create an APIC consumed API called services-api-sfcas-cases-assessment with SFCAS as the consumer using internet/oa3/b2b as the security template.

Expose 2 endpoints:

/waitingtime, which takes a payload in SFCAS format (yet to be defined). This call will then call the endpoint /calculatewaitingtime in the provided API after translation of the SFCAS model to the Assistance BOM model using the SFCAS → BOM translator library

/quote, which takes a payload in SFCAS format (yet to be defined). This call will then call the endpoint /getpatroltariffzone in the provided API after translation of the SFCAS model to the Assistance BOM model using the SFCAS → BOM translator library

Create an ACE application services-integration-assistance-cases-sfcas-assessment (CMDB: CMP35366)which will

Receive the SFCAS payload

Translate it to the Assistance BOM format using services-integration-shlib-transform-sfsc-bom and common-integration-shlib-datavalue-transcoding

Call the relevant endpoint on the provided API external-api-fsm-assistance-cases

Receive the FSM response in BOM format

Translate the BOM response back to the SFCAS Salesforce data model using services-integration-shlib-transform-sfsc-bom and common-integration-shlib-datavalue-transcoding

Return the translated SFCAS payload to the caller

All calls SFCAS → services-integration-assistance-cases-sfcas-assessment → external-api-fsm-assistance-case → services-integration-assistance-cases-sfcas-assessment → SFCAS are synchronous

Implement error handling in the ACE application according to the acceptance criteria:

Return 422 when SFCAS→BOM or BOM→SFCAS translation fails (AC2, AC3, AC10, AC11)

Return 502 when FSM returns a non-2xx response (AC4, AC12)

Return 504 when the FSM call times out (AC9)

All error responses must conform to the TCS ErrorTcs standard using the SFCAS(FUNC|TECH)[0-9]{4} error code convention (AC14, AC15)

Acceptance criteria

The following criteria apply to both use cases:

AC1: Given a well-defined SFCAS payload, a successful translation to BOM, and a successful call to the provided API, the result must be translated back to SFCAS format and returned to the caller. → HTTP 200

AC2: Given an SFCAS payload that cannot be translated to BOM format, the API must return early and inform the consumer of the nature of the problem. → HTTP 422

AC3: Given a successful SFCAS→BOM translation and a successful FSM response, but the BOM→SFCAS back-translation fails, the consumer must be informed of the error. → HTTP 422

AC4: Given a successful SFCAS→BOM translation, but the provided FSM API returns an error, the consumer must be informed of the upstream error. → HTTP 502

Input Validation

AC5: Given a request with an empty or missing body,
then the API must return 400 Bad Request with an ErrorTcs response describing the missing payload.

AC6: Given a request body that is not valid JSON,
then the API must return 400 Bad Request with an ErrorTcs response describing the parse error.

AC7: Given a request without the x-ibm-client-id header,
then the API must return 401 Unauthorized.

AC8: Given a request with an x-ibm-client-id that is not recognised or not authorised for this API,
then the API must return 403 Forbidden.

FSM Communication

AC9: Given a valid SFCAS payload
and a successful SFCAS→BOM translation,
but the FSM API does not respond within the configured timeout,
then the API must return 504 Gateway Timeout with an ErrorTcs response
where moreInformation indicates that the upstream FSM call timed out.

AC10 (POST /waitingtime only): Given a valid SFCAS→BOM translation
and a 200 response from FSM /calculatewaitingtime,
but the returned BOM case object contains no servicedelivery entry with a WaitingTime value,
then the API must return 422 Unprocessable Entity as the back-translation cannot produce a valid SFCAS response.

AC11 (POST /quote only): Given a valid SFCAS→BOM translation
and a 200 response from FSM /getpatroltariffzone,
but the returned BOM case object contains no onsiteservicedelivery entry with an AgreedTariffZone or CalculatedTariffAmount,
then the API must return 422 Unprocessable Entity as the back-translation cannot produce a valid SFCAS response.

AC12: Given a SFCAS payload that translates to a BOM case object missing the required field IncidentDateTime,
and FSM consequently returns 400 Bad Request,
then the API must return 502 Bad Gateway with an ErrorTcs response
where moreInformation conveys the upstream FSM rejection reason.
(Note: once the SFCAS data model is defined (NIPO-8415), the translation library application should detect this before calling FSM and return 422 instead. This AC must be revisited at that point.)

Rate Limiting

AC13: Given that the configured API plan rate limit has been exceeded,
then the API must return 429 Too Many Requests with an ErrorTcs response.

Observability

AC14: Given any error response (4xx or 5xx),
then the ErrorTcs object must include a populated gtid field
that is consistent across the full SFCAS → ACE → FSM call chain
to allow end-to-end tracing in logs.

AC15: Given any error response,
then the refAppError field must follow the pattern SFCAS(FUNC|TECH)[0-9]{4},
where SFCASFUNC codes are used for business and functional errors (translation failures, invalid payloads)
and SFCASTECH codes are used for technical errors (FSM unreachable, timeout, internal error),
and each distinct failure scenario must have a unique, stable error code.

Retry Safety

AC16: Given that SFCAS retries the same request with an identical payload after a 504 or network failure,
then the API must produce (the same result) as the original request with no side effects,
confirming that both POST /waitingtime and POST /quote are effectively idempotent.

Health Check

AC17: Given a GET /healthCheck request when the API is operational,
then the response must be 200 OK with body { "status": "UP" }.

Other information

The API will have the following endpoints:

POST /waitingtime

POST /quote

GET /healthCheck

The SFCAS data format is currently unknown; hence, no payload validation can be performed.

The shared library for translation between SFCAS and BOM formats is still under development.
